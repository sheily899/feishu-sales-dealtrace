# 飞书群聊 AI 销售沟通分析工作台：项目交付复盘与可复用经验

## 1. 文档目的

本文记录本项目从开源销售对话分析能力，到飞书群聊 AI 销售沟通分析工作台的完整改造过程。它用于两类场景：

- 面试复盘：说明项目解决的业务问题、本人承担的工程工作、关键设计取舍和验证方式；
- 后续复用：沉淀把“已有 AI 能力”改造成“可演示、可接入真实业务、可持续使用的产品原型”的方法。

本文描述的是当前单机 MVP 的真实能力，不把未完成的 CRM、多租户、云端部署或自动任务派发写成已经具备的功能。

## 2. 项目从什么问题出发

原始开源项目 `attentiontech/gtm-superintelligence` 能够分析销售对话转录文本，识别沟通类型、客户目标、销售表现和后续建议。但它的典型输入是人工整理后的通话文本，典型输出是命令行或结构化文件。

实际销售沟通常发生在飞书客户群。销售需要手工翻找消息、整理需求、确认承诺是否兑现，再决定下一步跟进动作。这带来三个问题：

1. 输入不自然：群聊内容需要复制、清洗和标注角色后才能分析；
2. 结果不直观：非技术销售人员难以直接从命令行或 JSON 获取可行动信息；
3. 信息不连续：每次重新分析只是生成新的报告，难以判断客户需求、风险和待办在后续沟通中发生了什么变化。

因此，本项目没有重写销售分析引擎，而是围绕已有能力补齐“业务输入、业务展示、持续状态”三层：

```text
飞书客户群 → 消息适配 → AI 销售分析 → 工作台报告 → 客户状态持续更新
```

## 3. 当前交付范围与边界

### 已交付

- 飞书测试群长连接接入和演示事件数据源；
- 客户/销售身份映射、消息过滤、去重、排序和标准对话生成；
- DeepSeek 驱动的中文销售沟通分析；
- 带原文证据定位的 Web 工作台；
- SQLite 本地持久化；
- 客户状态版本、变化记录和证据校验；
- 单销售管理多个客户群，按群独立查看和分析；
- 单元测试、接口测试、Golden Case 示例和使用文档。

### 明确不做

- 登录、权限、多租户和跨公司数据隔离；
- 完整 CRM、客户主数据或商机流程管理；
- 自动派发任务、日程同步、自动回复客户；
- 每条消息自动触发模型分析；
- 外部客户群、跨企业群权限与合规验证；
- 公网部署、云端数据库和生产级监控。

上述范围控制是有意为之：面试 MVP 的目标是证明端到端方案和工程判断，而不是在有限时间内建设完整销售系统。

## 4. 端到端工作流程

```text
客户、销售在飞书群正常发言
          ↓
机器人通过飞书长连接接收群消息
          ↓
根据预配置身份表识别客户/销售，过滤机器人消息
          ↓
按消息 ID 去重、按时间排序，构建标准销售对话
          ↓
销售在工作台选择客户群并手动点击“生成分析”
          ↓
DeepSeek 生成销售沟通分析与客户状态更新
          ↓
保存报告、状态快照、变化记录和证据关联
          ↓
工作台展示报告、原文依据、当前状态和版本时间线
```

“手动点击分析”是当前的重要产品决策。它让销售决定何时分析，避免每条群消息都调用模型，减少不必要的 Token 消耗，也避免频繁更新干扰实际沟通。

## 5. 已实现功能及其实现方法

### 5.1 DeepSeek 模型接入与中文输出

**解决的问题：** 原项目主要面向其他模型和英文销售场景。为了降低成本并适应中文飞书群聊，需要接入 DeepSeek 并让输出适合中文销售工作台。

**实现方法：**

- 将模型提供方设计为可配置项，默认使用 DeepSeek，同时保留原有模型兼容路径；
- 复用 OpenAI 兼容 SDK 调用 DeepSeek，不新建一套调用框架；
- 将 API Key 保留在本地 `.env`，通过 `.env.example` 提供字段说明，Git 忽略真实密钥；
- 在提示词中指定默认使用简体中文输出；
- 对模型常见的格式偏差做输入后规范化，例如将 `partially` 统一为系统接受的 `partial`，将单条证据统一转换为证据列表，并补全评分字段的兼容处理。

**面试表达：** 不是简单“换一个模型”，而是把低成本模型接入已有结构化 Workflow，并处理模型输出与严格数据契约之间的兼容问题。

### 5.2 飞书群聊消息适配

**解决的问题：** 销售和客户的真实对话在飞书群中，分析引擎需要的是有角色标签、顺序稳定的标准文本。

**实现方法：**

- 飞书机器人订阅群消息事件，并通过长连接接收消息，避免本地面试环境必须暴露公网回调地址；
- 使用本地 `FEISHU_ROLE_MAP` 将发送人映射为“客户”或“销售”，不让模型猜测身份；
- 只保留允许群中的文本消息，过滤机器人自身、未知身份、空消息和非群聊消息；
- 以消息 ID 去重，以时间戳和消息 ID 稳定排序；
- 输出统一文本格式：

```text
客户：我们主要担心 CRM 对接会不会很麻烦。

销售：可以先安排技术同事确认接口。
```

**面试表达：** 飞书层只做确定性的输入适配，AI 层只做语义判断。这使角色判断、顺序和去重可测试、可解释。

### 5.3 演示模式与真实飞书模式共用链路

**解决的问题：** 飞书权限、账号和测试群可能无法在面试现场稳定复现，不能让外部平台条件阻塞产品演示。

**实现方法：**

- 预置同飞书事件结构一致的 JSON 演示数据；
- 真实飞书消息和演示 JSON 都进入同一个标准化、存储、分析和展示流程；
- 页面明确标识数据来源是“飞书测试数据”还是“飞书测试群同步”。

**价值：** 演示模式不是伪造分析，而是替换消息来源；下游逻辑保持一致，因此既能用于自动化测试，也能作为真实接入不可用时的演示兜底。

### 5.4 销售沟通分析与群聊专属字段映射

**解决的问题：** 通用教练报告对销售不够直接，销售需要马上看到客户需求、顾虑、承诺和待办。

**实现方法：**

- 复用原项目的沟通阶段识别、客户目标、沟通评分和改进建议能力；
- 将输出映射为群聊工作台关注的字段：沟通阶段、客户需求、客户顾虑、销售回应覆盖、销售承诺、待办事项与下一步建议；
- 保留原分析报告中的销售表现与改进建议，避免因新增群聊字段丢失原项目价值；
- 将阶段 ID 映射为更适合业务展示的中文名称，例如“需求探索（Discovery）”。

**价值：** 不额外发明一套销售方法论，而是将已有分析引擎的结果转换为销售人员能直接使用的工作台语言。

### 5.5 原文证据定位与高亮

**解决的问题：** AI 结论如果没有可回看的原文，销售无法判断可信度，也难以在客户面前解释后续动作。

**实现方法：**

- 在消息标准化时保留 `messageId` 和对话片段信息；
- 分析结果中的引用文本与群消息做精确文本、包含关系匹配；
- 页面展示“原文依据”，点击后左侧聊天记录滚动到对应消息并高亮；
- 对无法定位的引用只展示文本，不伪造跳转。

**面试表达：** 这一步把“模型总结”变成“可追溯的业务结论”，是可信 AI 产品的重要基础。

### 5.6 Web 工作台

**解决的问题：** 命令行和 JSON 不适合作为销售日常使用界面，也不利于面试展示完整业务闭环。

**实现方法：**

- 使用轻量本地 Web 服务，避免为 MVP 引入独立前端工程、复杂构建工具或额外依赖；
- 页面顶部展示来源、同步情况和分析按钮；
- 左侧保留聊天记录作为事实证据，右侧作为分析报告主区域；
- 页面每三秒刷新本地同步状态；
- 所有飞书时间统一转为北京时间；
- 不在页面展示发送人的飞书 Open ID。

**价值：** 用最少的工程复杂度完成了“真实输入—分析—结果—证据”的可演示闭环。

### 5.7 本地 SQLite 持久化

**解决的问题：** 早期工作台的消息和报告仅保存在运行内存中，重启后丢失，不支持连续跟进。

**实现方法：**

- 本地 SQLite 保存群消息、最近报告、客户状态快照和状态变化记录；
- 所有数据都带 `chatId`，保证客户群之间查询隔离；
- 工作台启动时恢复已配置群的历史消息、最近报告和最新客户状态；
- 新群消息到达后只使该群的旧报告失效，等待销售再次手动分析；
- 数据文件放在 `data/workbench.sqlite3`，并由 `.gitignore` 排除，避免提交潜在客户对话。

**边界：** 这是本机面试演示存储，不等同于生产环境的加密、权限控制或云端备份。

### 5.8 客户状态跟踪

**解决的问题：** 单次报告只能说明“这段对话发生了什么”，不能说明客户关系在后续沟通中“发生了什么变化”。

**实现方法：**

系统为每个客户群维护一份结构化状态，包含：

- 当前阶段；
- 已识别需求；
- 未解决顾虑；
- 销售承诺；
- 待办事项及其状态；
- 相关角色；
- 商机风险；
- 已约定下一步。

每次销售手动分析时，系统执行：

```text
上一版客户状态 + 自上一版以来的新消息
→ 新的完整状态快照 + 本次变化记录
→ 保存为一个新版本
```

变化记录包括新增事项、已解决事项、待办状态迁移和当前跟进重点。历史版本不会被覆盖，因此可以回看客户关系如何演变。

**面试表达：** 项目从“群聊摘要工具”升级为“持续维护客户需求、风险、承诺和待办的销售跟进系统”。

### 5.9 状态变化证据校验与幂等性

**解决的问题：** 大模型可能在没有证据的情况下，把“待处理”错误标为“已完成”，或把仍存在的客户顾虑误判为已解决。

**实现方法：**

- 对“已完成”“已解决”“状态迁移”等高风险变化，要求模型返回本轮新增消息中的原文证据；
- 服务端保存前验证该证据文本是否确实存在于本轮新增对话；
- 证据不匹配时拒绝该变化，保留上一版状态，并在返回结果中记录拒绝原因；
- 若自上一版以来没有任何新消息，则跳过模型调用，直接返回已有状态并提示“暂无新消息”。

**价值：** 这同时解决了可信度和成本问题：既减少无依据的状态改写，也避免重复点击造成 Token 消耗。

### 5.10 多客户群管理

**解决的问题：** 销售通常同时跟进多个客户群，单群工作台无法展示真实工作场景。

**实现方法：**

- `FEISHU_GROUP_ALLOWLIST` 支持逗号分隔的多个群 ID，自动去重并拒绝空配置；
- 增加群摘要接口，返回每个已配置群的最新消息时间、当前阶段和待办数量；
- 以一个轻量多群分发器将每个 `chatId` 交给独立的单群工作台实例；
- 查询和分析接口携带 `chatId`，一个群的分析不会影响其他群的消息、报告或状态版本；
- 左侧客户群列表显示匿名名称“客户群 1、客户群 2”，不在可见页面暴露飞书群 ID；
- 页面初始不自动打开任何群，销售必须先选择客户群，再加载该群的聊天、报告与状态。

**边界：** 这是“单销售管理多个客户群”，不是多租户。所有数据仍在同一本地数据库中，尚无登录和权限隔离。

## 6. 开发过程中的问题、误区与纠正

### 6.1 误以为安装到全局 Python 就能解决运行依赖

**现象：** 页面调用 DeepSeek 时提示缺少 `openai` 包；在系统 Python 执行安装后，问题仍存在。

**原因：** 工作台实际使用项目 `.venv` 中的 Python，而不是系统 Python。不同解释器有不同依赖目录。

**纠正：** 通过打印实际 Python 路径和导入位置确认运行环境，在与工作台一致的虚拟环境中安装和验证依赖。

**可复用经验：** 遇到“明明安装了包但仍提示不存在”，优先核对“运行命令使用哪个 Python”，而不是重复安装。

### 6.2 大模型输出并不总是严格遵守结构化契约

**现象：** DeepSeek 早期返回中缺少评分名称、证据为字符串而不是列表、状态值写成 `partially`，导致 Pydantic 校验失败。

**原因：** 即使要求 JSON 输出，模型仍可能在枚举、可选字段和数组结构上产生轻微偏差。

**纠正：** 在模型结果进入业务模型前增加兼容性规范化；对于真正无法解释的数据，保持严格校验，不让错误数据进入页面或数据库。

**可复用经验：** 结构化 AI 输出应采用“两层防线”：提示词约束 + 服务端校验/有限规范化。不能只依赖提示词，也不能为了通过而放弃数据契约。

### 6.3 仅要求“中文输出”不足以保证所有字段中文

**现象：** 摘要已变中文，但客户目标等字段仍保留英文。

**原因：** 原分析框架中的固定 rubric 文本和模型生成文本来源不同，单一语言提示无法自动翻译所有已有字段。

**纠正：** 对固定阶段、状态和目标文案增加业务层中文映射；对模型生成部分保持中文提示。

**可复用经验：** 国际化需要区分“模型自由生成内容”和“系统固定枚举/模板内容”，分别处理。

### 6.4 飞书接入不是“拿到 App ID 就能收消息”

**现象：** 初期需要反复确认权限名称、事件订阅方式、机器人启用、测试群成员和身份 Open ID；消息到达后还出现“未知发送人”日志。

**原因：** 外部平台接入由应用权限、事件订阅、机器人入群、成员身份映射和本地服务同时决定，任何一层缺失都会导致表面上“没有消息”。

**纠正：** 将排查拆成明确顺序：应用创建 → 机器人启用 → 群权限 → 事件订阅 → 长连接日志 → 发送人身份映射 → 页面验证。未知发送人不进入分析，并输出可操作日志提示补充映射。

**可复用经验：** 第三方平台集成要先设计“最小可观测链路”，让每一步都有日志或可见结果，而不是一次性判断“接入失败”。

### 6.5 SDK 文档与实际安装版本存在差异

**现象：** 飞书长连接代码初次启动时因 SDK 构造参数不匹配而失败。

**原因：** 示例代码、文档和实际锁定依赖版本不一定完全一致。

**纠正：** 根据本地安装 SDK 的实际构造方式调整调用，并通过真实启动日志验证机器人身份与连接成功。

**可复用经验：** 对第三方 SDK，最终依据应是“当前环境安装的版本和实际运行结果”，不能只照搬网络示例。

### 6.6 初版页面暴露了内部 Open ID、群 ID，并且交互不够符合业务直觉

**现象：** 发送人曾显示 `ou_...`；多群列表初次显示 `oc_...`；页面还会自动打开第一个群，点击同一群没有可见反馈。

**原因：** 早期实现优先保障数据联通，把内部标识直接作为 UI 回退名称，忽略了面试展示和用户理解成本。

**纠正：**

- 将发送人统一显示为“客户/销售”；
- 客户群列表使用“客户群 1”等匿名名称；
- 页面初始要求用户主动选择群，选中后才展示聊天和报告；
- 保留 `chatId` 作为内部查询键，不作为面向销售的页面文案。

**可复用经验：** 内部标识符可以用于系统关联，但不应该默认成为用户界面语言。先问“用户需要理解什么”，再决定展示什么。

### 6.7 先做单次报告后才发现“连续跟进”才是产品差异

**现象：** 单次分析已经能生成较完整报告，但容易被理解为“ChatGPT 总结群聊”。

**原因：** 单次摘要没有保存上一次客户状态，也不能识别待办是否完成、顾虑是否新增、决策人是否出现。

**纠正：** 新增客户状态快照、变化记录、版本历史和证据校验，把分析从“重新总结”变成“基于新消息更新客户状态”。

**可复用经验：** 对持续发生的业务对话，核心产品价值往往不在一次回答，而在维护可验证的长期业务状态。

### 6.8 持久化文件被运行中的服务占用

**现象：** 为清除测试消息直接删除 SQLite 文件时失败。

**原因：** 正在运行的工作台仍持有数据库文件。

**纠正：** 先停止服务，再删除 `data/workbench.sqlite3`；下次启动时自动创建空数据库。功能实现和 `.env` 配置不受影响。

**可复用经验：** 数据清理是运维动作的一部分。先确认目标文件、确认服务是否停止、执行删除、再验证文件不存在。

### 6.9 pytest 默认临时目录权限异常

**现象：** 本地运行全量测试时，大量测试在 setup 阶段因 Windows 系统临时目录权限异常失败。

**原因：** pytest 的默认临时目录被占用或无访问权限，错误与业务代码无关。

**纠正：** 将 pytest 临时目录显式指定为项目内可写目录，例如：

```bat
python -m pytest -q --basetemp=.pytest-tmp
```

并将 `.pytest-tmp/` 加入 Git 忽略。

**可复用经验：** 先区分“测试断言失败”和“测试基础设施失败”。前者检查代码，后者检查环境、权限和运行进程。

## 7. 测试与验证方式

项目采用“薄切片：实现 → 测试 → 验证 → 提交”的方式推进。重点测试包括：

- 消息去重、排序、角色映射和机器人过滤；
- 飞书配置的多群解析、空配置拒绝和重复 ID 去重；
- SQLite 按 `chatId` 隔离消息、报告和客户状态；
- 客户状态版本递增、重启恢复、无新增消息跳过模型调用；
- 有原文证据的待办完成迁移可接受，无证据迁移会被拒绝；
- 多群摘要、指定群查询、默认群兼容行为和未配置群 404；
- 一个群分析不会影响另一个群的状态版本；
- 页面关键交互的静态契约，包括客户群选择、分析请求携带当前群和状态展示。

真实飞书部分已在测试群验证机器人身份解析、消息接收和页面同步。浏览器视觉验证目前以本地手工验证为主；若面向生产，需要补充端到端浏览器测试、真实负载测试和监控指标。

## 8. 面试中可以如何概括

### 30 秒版本

> 我基于开源销售对话分析引擎，增加了飞书群聊接入和 Web 工作台。机器人将客户与销售的群消息按角色、顺序和证据整理后交给 DeepSeek 分析，工作台展示需求、顾虑、承诺、待办和原文依据。后续我把它从单次总结升级为客户状态跟踪：系统只根据新增消息更新客户状态，并用原文证据约束“已完成/已解决”等高风险变化。最后增加多客户群管理，让一个销售能独立跟进多个群。

### 强调工程能力的版本

> 这个项目的重点不是重新训练模型，而是把已有 AI Workflow 工程化为业务闭环。我负责了飞书事件适配、身份映射、DeepSeek 结构化输出兼容、SQLite 持久化、证据追溯、状态版本控制、多群隔离和工作台展示。设计上把确定性规则放在适配层，把语义理解交给模型，并通过服务端证据校验限制模型无依据改写客户状态。

### 可主动说明的边界

> 当前是单机、单销售的面试 MVP，尚未建设登录、多租户、完整 CRM 和公网部署；这些是产品化下一阶段，而不是我回避的问题。当前优先验证了最核心的“真实群聊输入—可解释分析—持续客户状态—多群管理”链路。

## 9. 可复用的方法论

以下方法不依赖本项目，可复用于 AI、数据、自动化和业务系统项目。

### 9.1 先复用成熟能力，再补业务缺口

不要在已有成熟能力时从零实现模型、算法或平台。先明确：已有能力解决什么、缺什么输入、缺什么展示、缺什么持续状态，然后只补这几个缺口。本项目复用销售分析引擎，而不是重写销售方法论。

### 9.2 把系统拆成“确定性层”和“AI 语义层”

- 确定性层负责身份、权限、去重、排序、存储、格式转换和证据校验；
- AI 层负责理解需求、顾虑、风险和建议；
- 高风险业务状态由确定性规则兜底，不交给模型单独决定。

这样既能发挥模型优势，也能保证系统可测试、可解释和可控。

### 9.3 对持续业务构建“状态 + 变化”，不要只做摘要

任何持续发生的信息流，如客户沟通、项目管理、客服工单、招聘流程、供应链异常，都可以采用：

```text
上一版状态 + 新增信息 → 当前状态 + 变化记录
```

摘要回答“发生了什么”；状态和变化回答“现在处于什么阶段、什么需要行动、哪些风险变了”。后者更接近业务系统价值。

### 9.4 用证据约束 AI 的高风险结论

对于“完成、取消、审批、风险解除、金额变更”等会影响业务判断的结论，应要求模型提供原始证据，并由系统验证证据是否存在。没有证据时宁可保留原状态，也不要自动乐观更新。

### 9.5 用演示模式隔离外部依赖风险

外部平台账号、权限、网络和回调配置经常影响演示稳定性。应让真实模式和模拟模式共用下游处理链路，只替换输入来源。这样既能本地开发和自动化测试，也能在外部依赖失效时完成演示。

### 9.6 以薄切片交付并保留可验证提交

每个小能力都遵循：

```text
写失败测试 → 最小实现 → 跑聚焦测试 → 跑回归测试 → 独立提交
```

这比一次性改完所有文件更容易定位问题、回退改动和向面试官说明实施过程。提交历史本身也是项目管理和工程质量的证据。

### 9.7 把“用户可见语言”和“内部实现标识”分开

内部 ID、状态码、模型枚举和 SDK 对象不应直接出现在用户界面。产品界面要使用用户理解的名称、中文状态和清晰的空状态；内部标识保留在系统关联层。这个原则同时提升体验、隐私感受和面试展示质量。

### 9.8 区分代码问题、环境问题与产品边界

遇到失败时，先分类：

- 代码问题：用最小复现和测试修复；
- 环境问题：核对解释器、依赖、端口、临时目录、权限和运行进程；
- 外部平台问题：核对账号、权限、事件和配置；
- 产品边界：明确记录为下一阶段，而不是临时堆功能。

这种分类能避免在错误层面反复修补，也能让项目说明更可信。

## 10. 下一阶段建议

如果需要继续产品化，建议按以下顺序推进：

1. 建立 Golden Cases 和评测脚本，记录需求/顾虑/承诺/状态变化的准确率、召回率、证据正确率、延迟和 Token 消耗；
2. 将本地 SQLite 替换为具备备份和权限能力的云端数据库；
3. 增加登录、销售成员与租户隔离；
4. 增加飞书 OAuth 接入向导与连通性检测，而不是让用户把密钥交给模型；
5. 在销售确认后再接入 CRM、任务和日历等外部写入系统；
6. 最后再评估自动分析、通知和跨企业客户群接入的必要性与合规性。

这个顺序遵循“先验证质量，再扩展数据边界，最后自动化外部动作”的原则。
